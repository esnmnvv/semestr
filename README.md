# Семестр — планировщик студента

Первый этап проекта (20%) по «ТЗ_Планировщик_студента.docx»: регистрация, вход, выход, сессии, общая навигация и профиль. Интерфейс на русском языке, адаптирован от 360 px.

**По уточнённому требованию используется обычная PostgreSQL без Supabase.** Поэтому между браузером и базой добавлен небольшой сервер Node.js + Express. Браузер не получает строку подключения к БД. HTML, CSS, Bootstrap и обычный JavaScript сохранены; React и серверная генерация страниц не используются. Vite нужен только для разработки и сборки.

## Быстрый запуск на этом компьютере

```bash
cd semester-student-planner
npm ci
npm run db:local
npm run db:migrate
npm run dev
```

Открыть [http://localhost:5173](http://localhost:5173). Создать собственный аккаунт через «Создать аккаунт». Демонстрационных аккаунтов и паролей по умолчанию нет.

`db:local` запускает отдельный экземпляр PostgreSQL на `127.0.0.1:55432`, создаёт базу `semester`, ограниченную роль `semester_app` и локальный `.env` со случайными паролем БД и секретом сессий. Чужие базы и системная служба PostgreSQL не изменяются. Если `.env` существует, скрипт его не перезаписывает. Данные остаются в `.local/postgres` после закрытия сайта. Эти файлы исключены из Git.

Требования: Node.js 22.12+ и PostgreSQL 16+. Если PostgreSQL не обнаруживается, передать путь к каталогу её исполняемых файлов в `PG_BIN`. На macOS поддержаны стандартные пути Homebrew, на Linux — `/usr/lib/postgresql/16/bin` и `/usr/lib/postgresql/17/bin`. Запуск `initdb` от root не поддерживается.

Остановить веб-сервер: `Ctrl+C`. Остановить только созданный проектом экземпляр БД: `npm run db:stop`. Повторный запуск сохраняет аккаунты и данные.

## Подключение своей PostgreSQL

1. Создать базу и отдельную роль приложения с `LOGIN`, без `SUPERUSER`, `BYPASSRLS`, `CREATEDB` и `CREATEROLE`. Роль должна владеть базой и таблицами проекта.
2. Скопировать `.env.example` в `.env`. Указать `DATABASE_URL` и случайный `SESSION_SECRET` длиной не менее 32 символов. Не использовать демонстрационные значения из примера.
3. Указать `APP_ORIGIN`, точно совпадающий с адресом сайта: для разработки `http://localhost:5173`.
4. Выполнить `npm run db:migrate`, затем `npm run dev`.

Пример создания роли и базы администратором PostgreSQL (заменить пароль):

```sql
CREATE ROLE semester_app LOGIN PASSWORD 'replace-with-a-random-password'
  NOSUPERUSER NOBYPASSRLS NOCREATEDB NOCREATEROLE;
CREATE DATABASE semester OWNER semester_app;
```

Сгенерировать секрет: `node -e "console.log(require('node:crypto').randomBytes(48).toString('hex'))"`.

## Что реализовано

| Требование этапа 20%     | Реализация                                                                                                                        |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------- |
| Регистрация              | Имя, email, пароль, повтор пароля; серверная и клиентская проверка; имя 1–100 символов, пароль 8–128 символов                     |
| Уникальная почта         | Приведение к нижнему регистру и уникальный индекс PostgreSQL; понятная ошибка рядом с полем                                       |
| Вход и выход             | Проверка пароля, смена идентификатора сессии при входе, уничтожение сессии при выходе                                             |
| Сохранение пользователей | Таблица `users`, только хеши scrypt с индивидуальными солями; транзакционное создание пользователя и профиля                      |
| Сессии                   | Таблица `app_sessions`, срок 7 дней с продлением при активности, HttpOnly и SameSite cookie; сессия переживает перезапуск сервера |
| Профиль                  | Имя, почта только для чтения, изменение часового пояса; по умолчанию Asia/Bishkek                                                 |
| Сохранение настроек      | PostgreSQL, подтверждение после сохранения, восстановление после обновления и повторного входа                                    |
| Навигация                | Обзор, профиль, возврат ко входу при отсутствии сессии; будущие разделы явно помечены                                             |
| Ошибки                   | Сохранение введённых полей при сбое сети/БД, повторная отправка, сообщения без реквизитов БД                                      |
| Адаптивность             | Компьютер и телефон от 360 px, подписи полей, видимый фокус, управление клавиатурой                                               |

Предметы, задания, фильтры, календарь, уведомления и статистика не входят в этот этап и не реализованы. Лист расписания на странице входа — графическая иллюстрация, подписанная как пример. Обзор содержит только реальные сведения об аккаунте.

## Устройство проекта

```text
src/                  интерфейс, стили, клиент API и общая валидация
server/               API, доступ к БД, хеширование паролей
db/migrations/        SQL-схема, ограничения, триггер и RLS
scripts/              отдельная локальная PostgreSQL и миграции
tests/                модульные, API- и браузерные проверки
docs/                 описание дизайна, протокол и скриншоты
```

`users` хранит id, уникальную почту, хеш пароля и время регистрации. `profiles` связан с `users` один к одному и хранит имя, часовой пояс, даты создания и изменения. `app_sessions` хранит серверные сессии; в браузере остаётся только подписанный идентификатор в cookie.

Для `profiles` включены `ENABLE ROW LEVEL SECURITY` и `FORCE ROW LEVEL SECURITY`. Сервер в транзакции устанавливает `app.user_id` через `set_config(..., true)` из проверенной сессии. Значение сбрасывается при завершении транзакции. Id из тела запроса не используется для выбора профиля. Роль приложения не должна быть суперпользователем. Пароль и таблица сессий доступны только серверу, прямого SQL/API-доступа из браузера нет.

Запросы параметризованы. Смена часового пояса не изменяет даты регистрации: `created_at` хранится в `timestamptz`, меняется только отображение. Триггер PostgreSQL проверяет название часового пояса.

API: `POST /api/auth/register`, `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/session`, `GET /api/profile`, `PATCH /api/profile`. Ошибки возвращают `message` и при необходимости `errors` по полям. Для записывающих запросов нужны JSON, заголовок `X-Requested-With: Semester` и допустимый Origin. Чужие Origin отклоняются, CORS не включён. Лимит неудачных попыток авторизации — 20 за 15 минут на IP в одном процессе сервера.

## Проверка

```bash
npm test
npm run test:api
npm run test:e2e
npm run build
```

API- и браузерные тесты используют настроенную PostgreSQL, создают временные аккаунты `@example.test` и удаляют только свои записи. Запускать на базе разработки, не на рабочей базе пользователей. Для Chromium на новом компьютере: `npx playwright install chromium`. На текущем компьютере используется уже установленный браузер. Playwright автоматически запускает веб-сервер, если он ещё не работает. Скриншоты сохраняются в `docs/screenshots`.

Подробные результаты: [docs/testing.md](docs/testing.md).

## Размещение и резервная копия

Для обычной PostgreSQL нужен хостинг, поддерживающий **Node.js**, а не только статические файлы. Выполнить `npm ci`, `npm run db:migrate`, `npm run build`, затем `npm start`. Приложение слушает loopback; перед ним нужен reverse proxy с HTTPS. Задать `NODE_ENV=production`, `APP_ORIGIN=https://your-domain.example` и `TRUST_PROXY=1` только при одном доверенном прокси. В production cookie получает `Secure`, включаются CSP и HSTS. Для удалённой БД использовать TLS с проверкой сертификата по требованиям провайдера.

Секреты и `.local` не включать в репозиторий. Сервер и БД пока запущены локально; публикация в интернет в выполненный этап не входит. Подтверждение почты, восстановление и смена пароля также не входят в указанный первый этап.

Для резервной копии через настроенную среду PostgreSQL: `pg_dump -Fc -f semester.dump semester`. Восстанавливать сначала в отдельную базу: `pg_restore --no-owner --dbname=semester_restore semester.dump`. Роль восстановления должна иметь необходимые права; исходную базу этими командами не перезаписывать. Файлы копий содержат пользовательские данные и должны храниться отдельно от Git. Процедура восстановления на внешнем хостинге в этом этапе не испытывалась.

Документация библиотек: [Express sessions](https://expressjs.com/en/resources/middleware/session/), [Node.js crypto](https://nodejs.org/api/crypto.html), [PostgreSQL RLS](https://www.postgresql.org/docs/16/ddl-rowsecurity.html).
